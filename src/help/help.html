The inspector shows what the Swarm nodes hold for eth2swarm: Ethereum blocks stored as SOCs (the Block, Epoch, SOC and Bytes tabs) and the address index (the Address index tab). Everything it shows is checked with the same code the ethswarm command-line client uses, so a green check here means the client would accept the data too. Underlined terms link to the glossary.

The settings bar

The bar at the top applies to every tab.

  1. Node: the Bee or ant node the inspector reads from. Every chunk is fetched through it, so switching nodes shows what that node can retrieve. Each result says which node it came from.
  2. SOC owner: the owner, the Ethereum address of the key that imported the data. Every lookup except Bytes and a SOC lookup by address needs it. See where the owner comes from.
  3. Chain ID: which chain the data is about (1 = Ethereum mainnet, 1337 = the bee-factory dev chain). It is part of every identifier, so a wrong chain ID finds nothing.
  4. Trust anchor: the 32-byte trust anchor blocks are verified against. Leave it blank to use the owner's published anchor; the verdict is then amber, not green. The address index does not use it.
  5. Tabs: what to look at. The URL fragment (#block/97, #addr/lookup:…) names the view, so a view can be bookmarked or shared.
  6. reset settings: back to the node, owner, chain ID and anchor ethswarm serve was started with. Otherwise the browser keeps your own values, until ethswarm serve is restarted with a different default for that field.
  7. help: this page.

Where the owner comes from

The owner cannot be discovered from Swarm. A SOC's address is keccak256(identifier ‖ owner), so the data can only be found once the owner is known, and nodes have no "list owners" API. Choosing an owner is also choosing whom to trust. Ways to get it:

  • Start the inspector with it: ethswarm serve --owner 0x… or ETH2SWARM_OWNER=0x… fills the field for everyone who opens the page.
  • An export directory (addr-import --out <dir>): its addr1-export.json holds owner and chain_id.
  • The importer's key: cast wallet address --private-key $ETH2SWARM_KEY. addr-import and addr-upload also print the owner.
  • Any one of its SOCs: open it in the SOC tab by SOC address; the recovered signer is the owner.
  • The bee-factory dev chain: the Anvil dev key, 0xf39Fd6e51aad88F6F4ce6aB8827279cffFb92266, chain ID 1337.

Address index

The address index lists the transactions an Ethereum address appears in, newest first, without downloading the chain. The tab reads it as ethswarm addr-lookup does and checks every SOC signature, chunk and file reference on the way. The full design is docs/address-index.md.

How the index is built

Five nested ideas explain every number on this tab:

chain ──cut into──▶ units (64 blocks each)
units ──grouped into──▶ slices (L, i): 2^L units each, merged like a binary counter
slice ──hashed into──▶ buckets: one SOC each, about 2.8 KB
bucket ──holds──▶ address records: one per address, found by its fingerprint
record ──holds──▶ entries: (block, slot, roles), or a reference to a spill file
  • A unit is 64 finalized blocks. The head says how many units the index has (units), so it covers blocks up to units × 64 − 1.
  • A slice (L, i) holds units i·2L to (i+1)·2L − 1. Level 0 is one unit (64 blocks), level 10 is 1,024 units (65,536 blocks, about 9 days), level 16, the top, about 1.6 years. Slices are never changed: two neighbouring slices of one level are merged into a new one of the next level, like a binary counter carrying.
  • The few slices that together hold every unit exactly once are the cover. A lookup reads one bucket from each slice of the cover, so a full-history lookup costs a handful of chunks.
  • A slice spreads its addresses over buckets by their hash. Each bucket is one SOC holding the records of the addresses that hash into it. Records carry an 8-byte fingerprint, not the address itself.
  • A record's entries say where the address appears: the block, the slot (which transaction, or the block itself) and the roles (sender, recipient, log emitter, …). An address with many entries keeps them in a spill file instead.

Looking up an address

Type an address and press Look up. Here: vitalik.eth on the mainnet index.

  1. Address: the address to look up. Leave it blank to see only the index (its head and cover).
  2. Head units: blank uses the newest head found. A number reads the index as it was at that many units: the same slices and entries a client with that head would have seen.
  3. Since unit: blank reads everything. A unit number reads only what is newer, as an incremental sync does: fewer slices, and entries before that unit dropped.
  4. owner / chain: whose index this is and for which chain.
  5. covers: the blocks the index holds. An amber badge means the index starts at a later block: earlier blocks are not covered, which is not the same as "no entries there".
  6. head: the head update used and its units. In brackets, how it was found: the inspector probes head updates until one is missing.
  7. probe stopped at: the chunk whose fetch ended the search, with Bee's error. A read chunk failed (HTTP 500) here is normal: it is usually the next head update, which is not published yet.
  8. pending merges: merged slices still being uploaded. A lookup reads the smaller slices they replace instead, so this only costs a few more chunks. Usually none.
  9. origin: the origin, a copy of the index's first head, read once to know where head updates start.
  10. slices a lookup reads: the cover, newest first. Each (L, i) opens that slice.
  11. N appearances of …: how many entries the address has in the blocks looked at.
  12. blocks looked at: the block range the lookup read (with Since unit, only the newer part).
  13. slices / files read: how many slices were read, and how many files besides the buckets: spill files, and the pages file of a paged bucket. 0 files means every bucket and every record was inline.
  14. roles the index detects: which roles the importer looked for. Without trace, addresses that only occur inside internal calls (a multisig paying out, a router forwarding) are missing.
  15. slot: tx N is the transaction with index N in the block; block means the address appears in the block itself (fee recipient, withdrawal, uncle miner). See slot.
  16. roles: how the address took part, e.g. from (sent it), to (received it), topic (named in a log, typically a token transfer), word (an address-shaped value in the data). Several roles are joined with |. See roles.
What to look for. The newest entry should be close to the end of covers; the index runs up to about half an hour behind the chain, plus upload time. An entry's block and tx number find the transaction in any block explorer. An address with no entries gets "0 appearances", not an error: the buckets were read, and its fingerprint was not in them.

A slice

A click on a slice in the lookup opens its descriptor, the slice record.

  1. blocks: the blocks the slice holds. For the slice the index start falls into, this begins at the start, not at the slice's usual first block.
  2. last block hash: the hash of the slice's last block. This binds the slice to the chain: compare it with the block hash an explorer shows for that block.
  3. buckets: the bucket count B. Buckets 0 … B−1 all exist.
  4. addresses / appearances: distinct addresses in the slice, and its entries in total.
  5. buckets root: a Merkle root over all buckets. Two importers who built the same slice get the same root.
  6. roles detected: the roles the importer looked for in this slice.
  7. Bucket: open any bucket by number.
  8. The address's bucket: the bucket the looked-up address hashes into, which is the one a lookup reads.

A bucket

One bucket of a slice: the address records it holds. Here, the bucket of USDT's token contract in a level-6 slice.

  1. Bucket k of slice (L, i): which bucket this is. A paged bucket says so here, with its page count.
  2. fingerprint: the record's fingerprint, 8 bytes of the address's hash. The bucket does not store addresses: you can check that an address is in it, but not list who is.
  3. entries: how many entries the record has.
  4. block/slot · roles: the entries themselves when they fit inline: block/tx N or block/blk (the block itself), then the roles.
  5. address badge: the record whose fingerprint matches the address in the URL, the one a lookup reads.
  6. spill file: this record's entries did not fit (more than 256 bytes), so the bucket holds only their count and a reference to a spill file. The link opens it.
  7. An inline record: its entries are right here in the bucket.

A spill file

  1. Spill file — N entries: the record's full entry count. The view lists the newest 500, newest first.
  2. reference: the file's Swarm reference (open it in the Bytes tab to see the raw pages).
  3. block, slot, roles: as in a lookup. The busy token contracts are mostly emitter: they emit a Transfer log in every transaction that moves the token.

Below the reference, a read row says how the file was read: whole for a file of up to 256 MB, every entry checked against the count; newest pages only for a larger one (a token contract in a top-level slice), read from its last page backwards only as far as the view shows, so the count is the bucket record's and is not checked against the file.

Example addresses

Don't know an address with entries? Show example addresses counts well-known ones (tokens, the deposit contract, block builders; on a dev chain, the Anvil accounts).

  1. Show example addresses: runs the count.
  2. An address with entries is a link: a click looks it up as of the head the count used.
  3. entries: counted from the buckets alone, in parallel, without reading spill files. none in this period means the address is not in the blocks the index covers.

Block

Fetches the header record of block n and runs every check the client runs, one by one. It needs the owner and the chain ID; the trust anchor decides whether the verdict is green or amber.

  1. Block number: the block to fetch.
  2. ◀ ▶: previous and next block.
  3. Verdict: green ✓ verified against a pinned anchor; amber ⚠ verified, but only against the owner's published anchor, which trusts the publisher; red ✗ a check failed (the failing step says which).
  4. trust anchor: which anchor was used, pinned or published.
  5. fetch header SOC: the SOC address computed from the owner and the identifier string eth:<chain>:<anchor>:hdr:<n>, and its fetch.
  6. SOC signature: the chunk is signed by the owner.
  7. accumulator proof → anchor: the block hash, with the epoch and master proofs, hashes up to the anchor. This is the check that ties the block to the anchor.
  8. body matches header roots: the body hashes to the header's transactions, ommers and withdrawals roots.
  1. identifier string: the text whose keccak256 is the SOC's identifier.
  2. SOC address: keccak256(identifier ‖ owner), where the chunk lives.
  3. geometry: epochs × epoch size = the blocks the accumulator covers.
  4. block hash: keccak256 of the header's RLP, recomputed here (it is not stored).
  5. body ref: the Swarm reference of the block's body; the link opens it in the Bytes tab.
  6. epoch proof: sibling hashes from the block up to its epoch root.
  7. master proof: sibling hashes from the epoch root up to the master root, which with the geometry gives the anchor.
  8. Decoded header: the header fields. A parent hash links to the previous block.
  9. fields: how many fields the header has, which tells the fork it is from.

Epoch

Fetches an epoch's record and its header file and verifies every header in it.

  1. Verdict: as in the Block tab, for all headers of the epoch.
  2. signed by owner: the record's signature was checked against the configured owner. unverified means it was not, or failed.
  3. epoch root: the Merkle root over the epoch's block hashes.
  4. headers file: the Swarm reference of the epoch's concatenated headers.
  5. master proof: from the epoch root up to the anchor.
  6. body: what each block's body holds (txs, uncles, withdrawals), read from its header's roots; empty means nothing. A click on the number opens the block.

SOC

Any single SOC, decoded down to its fields. It recognises every eth2swarm record: block headers, epochs, the published anchor, and the address index's heads, slice descriptors and buckets.

  1. Mode: find the SOC by owner + identifier string, by owner + identifier in hex, or by its SOC address (owner optional).
  2. Input: the identifier string, identifier or address.
  3. Templates: fill in the identifier strings eth2swarm uses (hdr:<n>, epoch:<k>, accumulator, addr1:origin, addr1:slice:<L>:<i>).
  4. identifier: keccak256 of the identifier string.
  5. SOC address: keccak256(identifier ‖ owner).
  6. signature: the owner's signature over the identifier and the content address.
  7. span: the payload's length as the chunk declares it.
  8. signed CAC address: the content address of the payload that was signed (CAC).
  9. recovered signer: the address recovered from the signature. It is the owner; this is how a SOC reveals its owner.
  10. address = keccak(id ‖ signer): the chunk sits at the address its signer and identifier give. ✗ means it does not belong there.
  11. signer = configured owner: the signer is the owner in the settings bar. n/a when no owner was given.
  12. Payload: the raw payload in hex. Below the picture, the decoded record follows.

Bytes

Fetches a Swarm file by its reference (/bytes) and decodes it if it can: a block body, an epoch's header file, or text; otherwise a hex preview.

  1. Bytes reference: 64 hex characters, e.g. a body ref, headers file or spill file.
  2. size: the file's length and how many 4 KB data chunks it spans.
  3. decoded as: what the bytes were recognised as.
  4. The decoded content, here a block body: its transactions with recovered senders.

Node

The selected node's money: its wallet, its chequebook, what it has settled with its peers, and its postage batches. Everything is read with GET; the inspector sends no transaction. A deposit, a withdrawal or a top-up is shown as a curl command for you to run on the inspector's machine (the node URL is the one the inspector uses). The tab loads when first opened and again with Refresh or another node.

  • Wallet: the node's Ethereum address on its chain. xBZZ pays for postage batches and chequebook deposits; xDAI pays the gas of every transaction.
  • Chequebook: the contract the node pays its peers from with cheques. total is what it holds, available what is not promised yet: total minus the cheques sent, not cashed yet (a peer cashes a cheque when it chooses). paid by cheque sums the cheques sent and received; settled by time is the free allowance peers grant each other per second, which costs nothing. received, uncashed is what the node's own cheques from peers are still worth (checked for up to 32 peers).
  • xBZZ field: an amount in xBZZ, turned into the exact PLUR (1016 per xBZZ) of the deposit and withdraw commands.
  • Postage batches: the storage price is in PLUR per chunk per block (Gnosis blocks are 5 s, so a day is 17,280 blocks). A batch's cost per day is that price × 17,280 × 2depth; wallet pays is how many days the wallet's xBZZ would add to that batch alone. fullest bucket is the batch's fill: an immutable batch refuses the chunk that does not fit its fullest bucket. lifetime is Bee's estimate at the current price.
  • Top up: pick a batch and the days to add; the amount is PLUR per chunk, the cost that times 2depth. A top-up keeps the batch's depth and immutability.
  • Settlements with peers: the 50 peers settled with most, and the address the last cheque to each was made out to.
  • Warnings: a batch with under 7 days left, a fullest bucket 80 % full, a mutable or unusable batch, a chequebook with under a tenth of its total available, a wallet with under 0.01 xDAI. Not available lists the endpoints the node refused (a node without a chequebook refuses those).

The numbers are only as private as the inspector: anyone who can open it can read them.

Errors and warnings

MessageMeaning and what to do
owner address is requiredThe SOC owner field is empty. Enter the importer's address, or start ethswarm serve with --owner. See where the owner comes from.
no address index of owner … on chain … could be read from this node The origin was not found: a wrong owner, a wrong chain ID, or a node that cannot retrieve it. Check those three first.
read chunk failed (500 Internal Server Error)Bee could not find the chunk. It answers a chunk that does not exist and one it cannot reach the same way. Under probe stopped at it is expected (the next head update does not exist yet).
Amber ⚠ verdictVerified, but against the owner's published anchor. Pin an anchor to verify on your own terms.
unverified badgeThe record's signature was not checked against an owner (none was given) or did not match it.
earlier blocks are not coveredThe index starts at a later block; it says nothing about the blocks before.
slice (L, i) ends before the index startsThat slice holds only blocks before the index's start, so it was never written.

Glossary A–Z

Accumulator
The Merkle structure over all block hashes of the block store: one tree per epoch, and a master tree over the epoch roots. It hashes down to the trust anchor, so one 32-byte value vouches for every block.
Address index (addr1)
The index from an address to the blocks and transactions it appears in, stored on Swarm under the owner's key. addr1 is its format version: a change of its parameters would be a new name.
Addresses (count)
The number of distinct addresses in a slice, which is also its number of records.
Anchor, trust anchor
A 32-byte hash of the accumulator's master root and its geometry. Blocks verified against an anchor you pinned yourself are trusted only as far as that anchor is. It is also part of the block store's identifiers, so each import has its own set of SOCs.
Appearance
An address occurring at a (block, slot) in some role. All appearances of one address at one (block, slot) are merged into one entry.
Appearances (count)
The number of entries in a slice, or found for an address.
Block
In an entry: the block number the address appears in.
Body, body ref
A block's transactions, ommers (uncles) and withdrawals, stored as a Swarm file. The header record holds its reference (body ref); the body is checked against the header's roots.
Bucket
One SOC of a slice, holding the records of the addresses whose hash falls into it: about 2.8 KB, about 120–180 addresses. A lookup reads one bucket per slice. That the bucket also holds other addresses' records gives some privacy: a node that serves one bucket sees only that one of its addresses was asked for. The node a lookup goes through sees every bucket of the lookup and can narrow the address down much further (docs/address-index.md, Design constraints).
Bucket count (B)
How many buckets a slice has, chosen so a bucket averages 2,816 bytes. An address goes into bucket (first 4 bytes of keccak256(address) × B) >> 32.
Buckets root
A Merkle root over the hashes of all buckets of a slice. Two importers who build the same slice get the same root, so slices can be compared by this value. It does not prove a single bucket to a reader.
CAC (content-addressed chunk)
A Swarm chunk whose address is the hash of its content. A SOC signs the CAC address of its payload.
Chain ID
Which chain the data belongs to: 1 for Ethereum mainnet, 1337 for the bee-factory dev chain. It is part of every identifier string (eth:<chain>:…).
Cover
The set of slices that together hold every unit of the index exactly once: every complete top-level slice, then one slice for every set bit of the unit count, largest first. For an index from genesis that is at most (units ÷ 65,536) + 16 slices: 22 at most until late 2027. An index that starts at a later block reads only the slices after its start.
Emitter
The role of a contract that emitted a log in the transaction. Token contracts are emitters in every transfer of their token.
Entry
One line of an address's history: block, slot and roles. Entries are sorted by block and slot; the inspector shows them newest first.
Epoch
In the block store: a group of consecutive blocks (64 on bee-factory, 8,192 for mainnet geometry) with one Merkle tree. Not the beacon chain's epoch.
Epoch proof
The sibling hashes from a block hash up to its epoch root.
Epoch root
The Merkle root over the block hashes of one epoch.
Fingerprint (fp)
Bytes 4–11 of keccak256(address): how a record names its address without storing it. A lookup computes the fingerprint and looks for it in the bucket. Two addresses can share one by chance; verification against the chain sorts that out.
First block, start of an index
An index can start at a later block instead of genesis. Its head names that block, and the blocks before it are not covered: the index says nothing about them.
Geometry
Number of epochs × epoch size of the block store's accumulator. It is part of the anchor.
Head
The record that says how far the index goes: the number of units, the first and last block, the last block's hash and time, and the pending merges. A new head is published for every unit.
Head update
The head is a feed: update 0, 1, 2, … each at its own SOC. Update n announces the origin's units + n.
Header record
The SOC of one block: the header's RLP, the reference of its body, and the epoch and master proofs.
Identifier
32 bytes that, with the owner, give a SOC its address. eth2swarm makes an identifier the keccak256 of an identifier string, with one exception: a head update's is keccak256(topic ‖ n), where the topic is the keccak256 of eth:<chain>:addr1:head (Bee's sequence-feed scheme), so a head update cannot be opened by identifier string in the SOC tab, only by identifier or SOC address.
Identifier string
The readable name of a SOC, e.g. eth:1:0x…:hdr:97 (block 97), eth:1:addr1:origin or eth:1:addr1:bucket:6:6456:242.
Incremental sync (Since unit)
Reading only what is new since a unit already read: the slices of the cover that end after it, dropping older entries. A client a day behind reads up to 7 slices.
Level (L), index (i)
A slice's name (L, i): level L slices hold 2L units, and index i counts them from genesis. Level 0 = 64 blocks, level 6 = 4,096 blocks (about 14 hours), level 10 = 65,536 blocks (about 9 days), level 16 = about 1.6 years and is never merged again.
Master proof
The sibling hashes from an epoch root up to the master root of the accumulator.
Node
A Bee or ant node the inspector reads through. Different nodes can retrieve different chunks.
Origin
A fixed copy of head update 0 at a well-known identifier (eth:<chain>:addr1:origin). A reader starts there to learn the index's start and its first unit count.
Owner, SOC owner
The Ethereum address of the key that signed the data. Every SOC address depends on it, and every signature is checked against it. See where the owner comes from.
Paged bucket, pages file
A bucket whose records do not fit in one 4 KB chunk (rare: about 1 in 3,000) keeps them in a separate file of 4 KB pages; the bucket SOC holds only its count, page count and reference.
Payload
The data a SOC carries, up to 4,096 bytes: here always an eth2swarm record.
Pending merge
A merged slice the importer is still building or uploading. The head lists it, and readers use the smaller slices it replaces until it is done.
Probe
Fetching head update n+1, n+2, n+4, … until one is missing, then narrowing down, to find the newest head. A missing chunk costs a timeout in Swarm, so the inspector remembers the newest head per node, owner and chain and continues from there.
Published anchor
The anchor the owner publishes at eth:<chain>:accumulator. Convenient, but using it trusts the owner completely; the inspector shows such verdicts in amber.
Record, address record
One address's data in a bucket: its fingerprint, its entry count, and either the entries themselves (inline) or a spill file reference.
Recovered signer
The address computed from a SOC's signature. If the chunk is genuine, it is the owner.
Roles
How an address took part in a transaction or block. An entry can have several, joined with |:
RoleMeaning
fromsent the transaction
toits recipient, or the contract it created
emittera contract that emitted a log in it
topicnamed in a log topic, e.g. the sender or receiver of a token transfer
wordan address-shaped 32-byte value in the input, a log's data or an authorization; can be noise
tracein an internal call, creation or self-destruct (needs a tracing node)
blockin the block itself: fee recipient, uncle miner, withdrawal recipient
authsigned an EIP-7702 authorization in the transaction
A wallet that wants only what you took part in keeps from to topic trace block auth. Roles detected lists the roles the importer looked for at all.
Slice
An immutable part of the index holding the appearances of 2L units, named (L, i). Two slices of one level are merged into one of the next, up to level 16. See how the index is built.
Slice record, slice descriptor
The SOC describing a slice: its blocks, last block hash, bucket count, address and appearance counts, buckets root and detected roles. A reader needs it to find and decode the slice's buckets.
Slot
Where in the block the address appears. Slot 0 is the block itself (shown as block or blk); slot s > 0 is the transaction with index s − 1 (shown as tx s−1). So tx 131 is the 132nd transaction of the block, as block explorers count from 0.
SOC (single-owner chunk)
A Swarm chunk at an address computed from an identifier and an owner, signed by the owner. Anyone who knows both can find it, and the signature proves who wrote it. Every eth2swarm record is a SOC.
SOC address
keccak256(identifier ‖ owner): where a SOC is stored.
Span
The length of the data under a chunk, stored in the chunk. For a file's root chunk, the length of the whole file.
Spill file
A separate Swarm file holding the entries of one address in one slice, when they take more than 256 bytes. Busy addresses (token contracts, routers, builders) are spilled; the bucket keeps only the count and the reference. Page p of the file is its p-th 4096-byte chunk, so a file above 256 MB is read page by page rather than whole.
tx
The transaction index within a block, counted from 0 as block explorers do. See slot.
Unit
64 consecutive blocks, the smallest piece the index grows by. Unit u holds blocks 64·u … 64·u + 63. Units contain finalized blocks only, so the index runs about 13–32 minutes behind the chain, plus upload time.
Units (count)
How many complete units a head announces: the index covers blocks up to units × 64 − 1. Also the Head units field, which reads the index as of an older head.
Verdict
The Block and Epoch tabs' result: green ✓ verified against a pinned anchor, amber ⚠ verified against the published anchor, red ✗ a check failed.
